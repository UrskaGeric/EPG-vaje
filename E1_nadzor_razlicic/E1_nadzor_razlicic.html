Vaja 1: Nadzor različic z Gitom in GitHubom

Cilji vaje

Po tej vaji boste znali:

  • razložiti, kaj je nadzor različic (version control) in zakaj je pomemben za ponovljivo znanost (reproducible science),
  • ločiti med Gitom (orodje na vašem računalniku) in GitHubom (spletna storitev),
  • namestiti in nastaviti Git ter ga povezati z GitHub računom,
  • ustvariti repozitorij (repository), ga klonirati (clone) na računalnik ter uporabljati osnovne ukaze status, add, commit, push in pull,
  • uporabljati Git neposredno iz RStudia,
  • pripraviti svoj repozitorij za vaje EPG, kamor boste do konca semestra nalagali skripte iz vseh vaj.

Kaj je nadzor različic?

Verjetno poznate mapo, v kateri so datoteke analiza.R, analiza_v2.R, analiza_v2_popravljeno.R in analiza_KONCNO_res.R. Čez en mesec ne veste več, katera je prava in kaj ste v kateri spremenili. Nadzor različic (version control) to težavo reši sistematično: vsako pomembno spremembo shrani kot posnetek stanja projekta (snapshot), skupaj s časom, avtorjem in kratkim opisom.

Za raziskovalno delo je to pomembno, ker:

  • ponovljivost: vedno lahko pokažete, s katero različico skripte ste dobili rezultat v članku,
  • varnost: če nekaj pokvarite ali izbrišete, se vrnete na prejšnje delujoče stanje,
  • sodelovanje: več ljudi lahko dela na istem projektu, ne da bi si prepisovali datoteke,
  • varnostna kopija: kopija projekta je shranjena tudi na spletu, ne le na vašem prenosniku.

Večina orodij, ki jih bomo uporabljali v bioinformatiki (PLINK, R paketi, analizne verige, kot je Snakemake), je razvitih in objavljenih na GitHubu. Ob objavi članka revije vedno pogosteje zahtevajo, da je koda javno dostopna, najpogosteje prav v GitHub repozitoriju.

Git in GitHub

Git je program za nadzor različic, ki ga namestite na svoj računalnik. Spremembe beleži lokalno in deluje tudi brez interneta. GitHub je spletna storitev, ki gosti kopije Git repozitorijev. Omogoča deljenje, sodelovanje in varnostno kopijo.

Git GitHub
Kaj je program (orodje) spletna storitev
Kje teče lokalno (local), na vašem računalniku na spletu (github.com)
Kako ga uporabljamo ukazna vrstica (command line), RStudio, VS Code spletni brskalnik, GitHub Desktop
Namen beleženje različic datotek v repozitoriju hramba in deljenje kopije repozitorija, sodelovanje
Alternativa – (de facto standard) GitLab, Bitbucket

Git in GitHub se pogovarjata predvsem z dvema ukazoma: s push pošljete svoje spremembe na GitHub, s pull pa spremembe z GitHuba prenesete k sebi.

NasvetKljučna ideja

Git shranjuje posnetke stanja projekta (angl. commits) na vašem računalniku. GitHub hrani skupno kopijo te zgodovine na spletu, da se lahko z njo sinhronizirate (sync) vi (z več računalnikov) in vaši sodelavci (collaborators).

Git je porazdeljen sistem za nadzor različic (distributed version control system): vsak uporabnik ima na svojem računalniku celoten repozitorij z vso zgodovino (history) in delovno kopijo datotek (working copy). Strežnik (server) (npr. GitHub) je le skupna točka, prek katere se uporabniki sinhronizirajo.

Kako deluje Git: kje živi vaša koda

Pri delu z Gitom se datoteke premikajo med štirimi „prostori“:

Del Kje Kaj je
Delovna mapa (working directory) vaš računalnik mapa z datotekami, ki jih urejate (v RStudiu, VS Code, Excelu …)
Pripravljalno območje (staging area, index) vaš računalnik „čakalnica“ za spremembe, ki ste jih izbrali z git add
Lokalni repozitorij (local repository) vaš računalnik (skrita mapa .git) zgodovina vseh posnetkov (commitov) na vašem računalniku
Oddaljeni repozitorij (remote repository) npr. GitHub skupna kopija projekta na spletu

Spremembe ostanejo lokalne, dokler jih ne pošljete na GitHub s push. Spremembe drugih (ali svoje z drugega računalnika) prenesete s pull.

Ukaz pull je v resnici kombinacija dveh ukazov: fetch (prenesi spremembe z GitHuba v lokalni repozitorij) in merge (združi jih z vašimi datotekami v delovni mapi).

Spodnja slika povzema ukaze, ki premikajo spremembe med temi prostori. Večino jih bomo spoznali na vaji.

OpombaVsakodnevni cikel

Namestitev in nastavitev

GitHub račun

  1. Pojdite na https://github.com/ in izberite Sign up.
  2. Uporabniško ime izberite premišljeno, saj bo vidno v povezavah do vaših repozitorijev (npr. https://github.com/ime-priimek). Priporočamo ime, ki ga boste lahko uporabljali tudi kasneje v raziskovalnem delu.
  3. Kot študenti lahko zaprosite za brezplačen GitHub Education paket (Student Developer Pack). Za vaje ga ne potrebujete, je pa uporaben.

Namestitev Gita

Windows: prenesite Git z https://git-scm.com/download/win in ga namestite s privzetimi nastavitvami. Skupaj z Gitom se namesti tudi Git Bash, ukazna vrstica, v kateri bomo izvajali ukaze, in Git Credential Manager, ki poskrbi za prijavo v GitHub.

macOS: odprite aplikacijo Terminal in vpišite git --version. Če Git še ni nameščen, vas bo sistem vprašal, ali želite namestiti Command Line Developer Tools. Potrdite.

Linux: sudo apt install git (Ubuntu/Debian).

Preverite, ali namestitev deluje. Odprite Git Bash (Windows) ali Terminal (macOS/Linux) in vpišite:

git --version
git version 2.46.0.windows.1

Prva nastavitev: kdo ste

Git vsak commit podpiše z imenom in e-naslovom. To nastavite enkrat na vsakem računalniku. Uporabite isti e-naslov kot pri GitHub računu:

git config --global user.name "Ime Priimek"
git config --global user.email "vas.naslov@primer.si"
git config --global init.defaultBranch main

Zadnja vrstica poskrbi, da se glavna veja v novih repozitorijih imenuje main (enako kot na GitHubu).

Nastavitve preverite z:

git config --global --list
NasvetNastavitev iz R

Isto lahko naredite tudi v R konzoli s paketom usethis:

install.packages("usethis")
usethis::use_git_config(user.name = "Ime Priimek",
                        user.email = "vas.naslov@primer.si")

Prijava v GitHub iz računalnika (authentication)

GitHub za push ne sprejme več gesla vašega računa. Potrebuje varno prijavo:

  • Windows: ob prvem git clone (zasebnega repozitorija) ali git push se odpre okno Git Credential Manager. Izberite Sign in with your browser in potrdite dostop v brskalniku. Prijava se shrani, zato tega ne boste več ponavljali.
  • macOS/Linux ali če zgornje ne deluje: ustvarite osebni dostopni žeton (Personal Access Token, PAT) in ga shranite. Najlažje to naredite iz R:
install.packages(c("usethis", "gitcreds"))
usethis::create_github_token()   # odpre GitHub v brskalniku; ustvarite žeton in ga kopirajte
gitcreds::gitcreds_set()         # prilepite žeton, ko vas vpraša
OpozoriloŽeton je kot geslo

Žetona nikoli ne zapisujte v skripte in ga ne nalagajte na GitHub.

Prvi repozitorij v Git Bashu

Najprej se naučimo ukaze v ukazni vrstici. Tako boste razumeli, kaj se dogaja v ozadju, ko boste kasneje klikali gumbe v RStudiu.

Ustvarite repozitorij na GitHubu

  1. Na GitHubu kliknite + (desno zgoraj) → New repository.
  2. Izpolnite:
    • Repository name: npr. git-vaja
    • Visibility: Private ali Public
    • obkljukajte Add a README file. README je „domača stran“ repozitorija s kratkim opisom projekta.
  3. Kliknite Create repository.

git clone: prenesite repozitorij na računalnik

Na strani repozitorija kliknite zeleni gumb Code in kopirajte HTTPS naslov. Na voljo so še druge možnosti:

Možnost Kdaj jo uporabimo
HTTPS kloniranje z ukazom git clone (Git Bash, RStudio)
Open with GitHub Desktop če raje uporabljate grafični program
Download ZIP enkraten prenos brez zgodovine Gita. Pri vajah tega ne uporabljajte.

V Git Bashu se premaknite v mapo, kjer želite imeti svoje projekte, in klonirajte repozitorij:

mkdir -p ~/Documents/GitHub
cd ~/Documents/GitHub
git clone https://github.com/UPORABNISKO-IME/git-vaja.git
Cloning into 'git-vaja'...
remote: Enumerating objects: 3, done.
remote: Counting objects: 100% (3/3), done.
remote: Total 3 (delta 0), reused 0 (delta 0), pack-reused 0
Receiving objects: 100% (3/3), done.

Premaknite se v novo mapo repozitorija:

cd git-vaja

Git Bash v vrstici z ukazom pokaže nekaj koristnih informacij: zeleno uporabniško ime in računalnik, rumeno trenutno mapo in, kadar ste v Git repozitoriju, modro trenutno vejo (branch, npr. (main)).

git status: kaj se je spremenilo?

git status je ukaz, ki ga boste uporabljali najpogosteje. Pokaže stanje delovne mape glede na zadnji commit.

git status
On branch main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean

V mapo dodajte novo datoteko, npr. scripts/test.R (ustvarite mapo scripts in v njej prazno datoteko). Ponovno poženite git status:

On branch main
Your branch is up to date with 'origin/main'.

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        scripts/

nothing added to commit but untracked files present (use "git add" to track)

Nove datoteke, ki jih Git še ne spremlja (untracked), so izpisane rdeče.

git add: pripravite spremembe (stage)

git add scripts/test.R   # ena datoteka
git add .                # vse spremembe v trenutni mapi (previdno!)

Ponovno preverite z git status. Datoteke, pripravljene za commit, so izpisane zeleno:

Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
        new file:   scripts/test.R

git commit: shranite posnetek stanja (commit)

git commit -m "Dodaj testno skripto"
[main 0c879b4] Dodaj testno skripto
 1 file changed, 0 insertions(+), 0 deletions(-)
 create mode 100644 scripts/test.R

Vsak commit dobi enolično oznako (hash, tukaj 0c879b4), po kateri se lahko kasneje vrnete nanj.

NasvetDobro sporočilo commita

Sporočilo naj na kratko pove, kaj ste spremenili, npr. Dodaj filtriranje SNP-jev po MAF ali Popravi os y na PCA grafu. Izogibajte se sporočilom, kot so popravki, asdf ali nova verzija. Čez en mesec iz njih ne boste vedeli ničesar.

Bližnjica: git commit -a

git commit -a -m "Posodobi obstoječe skripte"

Ukaz v enem koraku pripravi in shrani spremembe že spremljanih datotek. Novih datotek (untracked) ne doda. Dokler se ne navadite, raje uporabljajte ločena koraka git add in git commit.

git push: pošljite (push) spremembe na GitHub

git push
To https://github.com/UPORABNISKO-IME/git-vaja.git
   c82b3ae..0c879b4  main -> main

Osvežite stran repozitorija na GitHubu. Nova datoteka in commit sta zdaj vidna tudi tam.

git pull: prenesite (pull) spremembe z GitHuba

Na GitHubu v brskalniku uredite datoteko README.md (ikona svinčnika → Commit changes). S tem simulirate spremembo, ki jo je naredil nekdo drug ali vi na drugem računalniku. Nato na računalniku:

git pull
Updating 0c879b4..5e1a2f3
Fast-forward
 README.md | 2 ++
 1 file changed, 2 insertions(+)

Če na GitHubu ni nič novega, Git izpiše Already up to date.

OpozoriloDobra navada

Na začetku vsakega dela najprej poženite git pull, šele nato začnite urejati datoteke. Tako se izognete konfliktom (merge conflicts).

git log in git diff: zgodovina (log) in razlike (diff)

git log --oneline     # kratek seznam vseh commitov
git diff              # kaj ste spremenili, a še niste dodali z git add
git diff --staged     # kaj je pripravljeno za naslednji commit
5e1a2f3 (HEAD -> main, origin/main) Update README.md
0c879b4 Dodaj testno skripto
c82b3ae Initial commit

git init: nov repozitorij iz obstoječe mape

Če imate projekt že na računalniku in ga želite šele zdaj dati pod nadzor različic:

cd pot/do/projekta
git init
Initialized empty Git repository in .../projekt/.git/

Git ustvari skrito mapo .git, v kateri hrani vso zgodovino (HEAD, objects, refs …). Te mape ne urejajte ročno in je ne brišite, saj s tem izbrišete celotno zgodovino.

Da lokalni repozitorij povežete z GitHubom, na GitHubu ustvarite prazen repozitorij (brez README) in nato:

git remote add origin https://github.com/UPORABNISKO-IME/projekt.git
git push -u origin main
Opombaclone ali init?
  • git clone: kopija obstoječega repozitorija z GitHuba. To je najpogostejši način in ga bomo uporabljali na vajah.
  • git init: nov lokalni repozitorij, ki ga kasneje povežete z GitHubom.

Git v RStudiu

Na vajah bomo delali v RStudiu, ki ima vgrajen zavihek Git. Ukazi so enaki kot v Git Bashu, le da jih izvajate s klikom.

Povežite RStudio z Gitom

  1. Tools → Global Options → Git/SVN.
  2. Obkljukajte Enable version control interface for RStudio projects.
  3. V polju Git executable mora biti pot do Gita, na Windows običajno C:/Program Files/Git/bin/git.exe. Če je polje prazno, poiščite datoteko s Browse.
  4. Ponovno zaženite RStudio.

Nov RStudio projekt iz GitHub repozitorija

  1. File → New Project → Version Control → Git.
  2. V Repository URL prilepite HTTPS naslov repozitorija z GitHuba.
  3. Izberite mapo (Create project as subdirectory of), npr. Documents/GitHub.
  4. Kliknite Create Project.

RStudio repozitorij klonira, ustvari v njem RStudio projekt (.Rproj) in ga odpre. Desno zgoraj se pojavi zavihek Git.

Zavihek Git

Gumb / stolpec Ukaz v Gitu Kaj naredi
kljukica Staged git add pripravi datoteko za commit
Diff git diff pokaže spremembe po vrsticah (zeleno dodano, rdeče izbrisano)
Commit git commit odpre okno, kjer napišete sporočilo in shranite posnetek
Push (zelena puščica gor) git push pošlje commite na GitHub
Pull (modra puščica dol) git pull prenese spremembe z GitHuba
ura (History) git log pokaže zgodovino commitov

Pomen črk v stolpcu Status: ? nova datoteka, ki je Git še ne spremlja; A dodana; M spremenjena (modified); D izbrisana.

NasvetTerminal v RStudiu

RStudio ima poleg konzole tudi zavihek Terminal (Tools → Terminal → New Terminal). Na Windows ga lahko nastavite tako, da uporablja Git Bash (Tools → Global Options → Terminal → New terminals open with: Git Bash). Vse ukaze iz prejšnjega poglavja lahko tako izvajate kar v RStudiu. Isti terminal bomo uporabljali na naslednji vaji za PLINK.

Vaš repozitorij za vaje EPG

Do konca semestra boste vse skripte, poročila in odgovore z vaj nalagali v en repozitorij. Ta bo hkrati vaša oddaja in vaša osebna zbirka kode, ki jo boste lahko uporabili tudi kasneje, npr. pri magistrski nalogi.

Ustvarite repozitorij

  1. Na GitHubu ustvarite nov repozitorij z imenom EPG-2026-priimek (npr. EPG-2026-novak).
  2. Nastavitve:
    • Private
    • obkljukajte Add a README file
    • Add .gitignore → izberite predlogo R
  3. Dodajte asistentko kot sodelavko (collaborator): Settings → Collaborators → Add people → UrskaGeric.
  4. Repozitorij odprite kot nov projekt v RStudiu (File → New Project → Version Control → Git).

Struktura repozitorija

Ustvarite mape za vse vaje. Prazne mape Git ne spremlja, zato bodo na GitHubu vidne šele, ko vanje shranite prvo datoteko.

EPG-2026-priimek/
├── README.md              # kdo ste, kaj je v repozitoriju
├── .gitignore             # datoteke, ki jih Git ne nalaga na GitHub
├── EPG-2026-priimek.Rproj
├── E1_git/
├── E2_plink/
├── E3_raznolikost/
├── E4_struktura/
├── E5_inbriding/
└── data/                  # podatki (NE gredo na GitHub!)

.gitignore: česa ne nalagamo na GitHub

Datoteka .gitignore pove Gitu, katerih datotek naj ne spremlja. To je pri populacijski genomiki zelo pomembno:

  • GitHub zavrne datoteke, večje od 100 MB. VCF datoteka z orli, s katero bomo delali, ima skoraj 600 MB.
  • Podatki se med analizo ne spreminjajo in so že shranjeni drugje (npr. v repozitoriju Dryad ob članku). Na GitHub sodi koda, ki iz podatkov naredi rezultate.
  • Vmesne datoteke (PLINK .bed, .bim, .fam, .log …) lahko kadar koli ponovno izračunate s svojo skripto.

Na konec datoteke .gitignore (predloga R že vsebuje .Rhistory, .RData in .Rproj.user/) dodajte:

# --- podatki in vmesne datoteke (EPG) ---
data/
*.vcf
*.vcf.gz
*.bed
*.bim
*.fam
*.ped
*.map
*.raw
*.log
*.nosex
*.exe

# --- renderirani izhodi Quarto/Rmarkdown ---
*_files/
*.html
OpombaKaj pa, če želim oddati HTML poročilo?

Če želite poročilo oddati na GitHub, izbrišite vrstico *.html. Pri Quarto dokumentih je pri tem priporočljivo v glavo dodati embed-resources: true, da je vse (tudi slike) v eni HTML datoteki in mape *_files/ ne potrebujete.

OpozoriloČe je velika datoteka že v commitu

Če ste veliko datoteko pomotoma že dodali v commit, push ne bo uspel, tudi če jo kasneje dodate v .gitignore. V tem primeru prosite za pomoč. Rešitev je, da zadnji commit razveljavite (git reset --soft HEAD~1), datoteko odstranite iz pripravljalnega območja (git rm --cached datoteka) in commit ponovite.

Pravilo za vse naslednje vaje

PomembnoPo vsaki vaji
  1. pull na začetku dela,
  2. shranite skripte in poročila v mapo vaje,
  3. commit z opisnim sporočilom (lahko večkrat med vajo),
  4. push na koncu dela.

Stanje vašega repozitorija na GitHubu je hkrati vaša oddaja.

Ko gre kaj narobe: razveljavljanje sprememb (undo)

Situacija Ukaz
Spremenil/a sem datoteko in želim nazaj zadnjo shranjeno različico git restore datoteka.R
Datoteko sem dodal/a z git add, pa je ne želim v commitu git restore --staged datoteka.R
Zadnji commit ima napačno sporočilo (še ni bil poslan s push) git commit --amend -m "Novo sporočilo"
Želim razveljaviti commit, ki je že na GitHubu git revert <hash> (ustvari nov commit, ki spremembe izniči)
Opozorilo

git restore datoteka.R nepreklicno zavrže neshranjene spremembe v datoteki. Pred uporabo preverite z git diff.

Ko dva delata hkrati

Kaj se zgodi, ko dva človeka (Ana in Bor) delata na istem repozitoriju in oba pošljeta spremembe na GitHub?

Zakaj je to dobro:

  • nihče ne more po nesreči prepisati dela drugega: Git zavrne push, dokler nimate vseh sprememb z GitHuba,
  • delo obeh se ohrani: po git pull sta v zgodovini oba commita, C in D,
  • Git večino združevanja naredi sam; vašo pomoč potrebuje samo pri konfliktu.

Isto se zgodi tudi, če delate sami na dveh računalnikih (npr. doma in na fakulteti). Zato velja pravilo: pred začetkom dela vedno git pull.

Konflikti

Konflikt nastane, kadar je bila ista vrstica iste datoteke spremenjena na dveh mestih (npr. na GitHubu in na vašem računalniku). Ob pull vam Git v datoteko vpiše oznake:

<<<<<<< HEAD
plot(pca$x[, 1], pca$x[, 2], col = "blue")
=======
plot(pca$x[, 1], pca$x[, 2], col = "red")
>>>>>>> origin/main

Zgornji del je vaša različica, spodnji različica z GitHuba. Ročno pustite pravo vrstico, izbrišite oznake <<<<<<<, ======= in >>>>>>>, nato pa git add, git commit in git push.

Pri delu v svojem repozitoriju z enega računalnika se konfliktom izognete, če dosledno uporabljate cikel pull → delo → commit → push.

Veje (branches)

Veje omogočajo, da razvijate nove stvari ali preizkušate ideje, ne da bi pokvarili delujočo glavno različico (main). Pri vajah boste delali večinoma na main, veje pa so osnova vsakega skupinskega projekta.

  • main naj ostane čim bolj stabilna,
  • vsaka oseba ali vsaka nova funkcija dobi svojo vejo,
  • ko je delo končano in preverjeno, vejo združimo (merge) nazaj v main.

Ustvarjanje in preklapljanje med vejami

git branch                 # seznam lokalnih vej (* = trenutna)
git switch -c nov-graf     # ustvari novo vejo in se premakni nanjo
git switch main            # vrni se na main
git branch -d nov-graf     # izbriši vejo (ko je že združena)
Opombagit switch ali git checkout?

V starejših navodilih in na slikah boste pogosto videli git checkout (git checkout -b nova-veja). Ukaz deluje, vendar opravlja dve različni nalogi: preklaplja med vejami in obnavlja datoteke, kar začetnike zmede. Novejša Git ukaza ju ločita: git switch za veje, git restore za datoteke. Na vajah uporabljamo switch.

Primer dela na veji

git switch -c nov-graf
# ... urejate datoteke ...
git add .
git commit -m "Dodaj PCA graf z barvami po državah"
git push -u origin nov-graf

Ob prvem push nove veje vam GitHub izpiše povezavo za odprtje zahteve za združitev (Pull Request). To je predlog, da se veja združi v main, ki ga lahko pregledajo sodelavci.

Združevanje (merge): git merge

Premaknite se na vejo, ki jo želite posodobiti (običajno main), in vanjo združite drugo vejo:

git switch main
git merge nov-graf
git push
Updating 0c879b4..a09a19b
Fast-forward

 1 file changed, 12 insertions(+)

OpozoriloUrejanje neposredno na GitHubu

Na GitHubu lahko datoteke urejate tudi v brskalniku. To je primerno za manjše popravke datoteke README, ne pa za kodo, saj je pred commitom ne morete pognati in preveriti.

Povzetek ukazov (cheat sheet)

git config --global user.name "Ime Priimek"   # enkratna nastavitev
git config --global user.email "naslov"

git clone <url>              # kopija repozitorija z GitHuba
git init                     # nov lokalni repozitorij
git status                   # kaj se je spremenilo
git add <datoteka>           # pripravi datoteko za commit
git add .                    # pripravi vse spremembe v mapi
git commit -m "sporočilo"    # shrani posnetek stanja
git push                     # pošlji commite na GitHub
git pull                     # prenesi in združi spremembe z GitHuba
git log --oneline            # zgodovina commitov
git diff                     # neshranjene spremembe

git restore <datoteka>       # zavrzi spremembe v datoteki
git restore --staged <dat.>  # odstrani datoteko iz pripravljalnega območja

git branch                   # seznam vej
git switch -c <ime>          # ustvari vejo in se premakni nanjo
git switch <ime>             # premakni se na obstoječo vejo
git merge <ime>              # združi vejo v trenutno vejo
git branch -d <ime>          # izbriši vejo

Uradni povzetek ukazov z GitHuba (dve strani, v angleščini) si natisnite ali shranite: Git cheat sheet (PDF).

  3. Repozitorij odprite kot projekt v RStudiu.
  4. Ustvarite mape E1_git, E2_plink, E3_raznolikost, E4_struktura, E5_inbriding in data.

Domača naloga: priprava na vajo 2

Na vseh naslednjih vajah bomo analizirali genomske podatke orla belorepca (Haliaeetus albicilla) iz članka:

Hansen, C. C. R., Láruson, Á. J., Rasmussen, J. A., et al. (2023). Genomic diversity and differentiation between island and mainland populations of white-tailed eagles (Haliaeetus albicilla). Molecular Ecology, 32, 1925–1942. https://doi.org/10.1111/mec.16858

Članek je prosto dostopen (open access): PDF članka. Preberite ga in v svojem repozitoriju ustvarite datoteko E1_git/clanek_orli.md, v kateri na kratko (v nekaj stavkih) odgovorite na vprašanja:

  1. Katero je glavno raziskovalno vprašanje članka? Zakaj je zanimivo, da je vrsta z veliko sposobnostjo razširjanja genetsko strukturirana?
  2. Iz katerih držav so vzorci? Katere populacije so otoške in katere celinske?
  3. Kaj so historični vzorci in zakaj so jih avtorji vključili poleg sodobnih?
  4. Kakšen tip podatkov so uporabili (sekvenciranje, število SNP-jev) in kako so podatke filtrirali?
  5. Naštejte analize, ki so jih naredili (npr. genetska raznolikost, FST, PCA, ADMIXTURE, inbriding, efektivna velikost populacije). Katera slika ali tabela prikazuje rezultat posamezne analize?
  6. Kakšne so glavne ugotovitve glede raznolikosti in inbridinga otoških populacij v primerjavi s celinskimi?
  7. Kateri štirje zgodovinski dogodki naj bi oblikovali upad efektivne velikosti populacij?
  8. S svojimi besedami razložite pojme: učinek ustanovitelja, genetski drift, inbriding, filopatrija, efektivna velikost populacije (Ne).

Datoteko oddajte s commit in push pred začetkom vaje 2. Na vajah 2–5 bomo nekatere od teh analiz ponovili sami in na koncu preverili, ali pridemo do enakih zaključkov kot avtorji.

Za radovedne: delo v skupini

Pri večjih projektih z več sodelavci se ekipa dogovori o pravilih za veje. Preprosta pravila, ki preprečijo veliko težav:

  1. ne eksperimentirajte neposredno na main,
  2. pred začetkom dela vedno pull,
  3. za vsako novo stvar ustvarite vejo z opisnim imenom (nov-graf, popravek-readme),
  4. vejo združite šele, ko koda deluje,
  5. pišite smiselna sporočila commitov.

Eden bolj znanih dogovorov je Git flow:

Veja Vloga
main stabilna, objavljena koda
develop sproten razvoj, združevanje novih funkcij
feature/* nove funkcije (iz develop)
release/* priprava nove različice (iz develop)
hotfix/* nujni popravki (iz main)

Merge ali rebase?

Oba ukaza združita delo z ene veje v drugo, vendar zgodovino obravnavata različno.

Merge ohrani dejansko zgodovino in ustvari dodaten commit, ki veji združi:

A---B---C---F    (main, F = merge commit)
         \ /
          D---E  (veja)

Rebase vaše commite „presadi“ na konec druge veje, zato je zgodovina linearna. Pri tem se spremenijo oznake (hash) commitov:

A---B---C---D'---E'
Merge Rebase
Zgodovina ohrani veje linearna, preglednejša
Varnost na skupnih vejah varnejši lahko zmede sodelavce
Konflikti rešite enkrat lahko pri vsakem commitu posebej

Na vajah uporabljamo merge. Rebase je koristen, ko osnove sodelovanja že dobro obvladate.
